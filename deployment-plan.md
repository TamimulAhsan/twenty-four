# Deployment: one codebase, two environments

How the same code, the same manifests and the same commands serve local
development and a real market, and what genuinely has to differ between them.

Reference: [`system-architecture.html`](system-architecture.html) §2 for the
deployment topology and §17 for the stack, [`CLAUDE.md`](CLAUDE.md) for the
decisions this must respect, [`backend-plan.md`](backend-plan.md) for what is
built.

---

## Where we are

Everything runs on one k3s node with one command set. There is no second
environment, and the reason is not that it was forgotten: nothing yet
distinguishes the two, so every value that should differ is written into a file
that is shared.

Counted rather than estimated: **45 hardcoded development values in
`deploy/`** and **25 more in `scripts/`**. The registry, the namespace, the
hostnames, the passwords, the replica counts and two development-only web
surfaces are all literals in the manifests that would be applied to production.

The goal is not to fork them. It is to make the difference small, explicit, and
in one place.

---

## What actually differs

The useful question is not "what changes" but "what changes for a reason". Most
of the system is genuinely identical, and saying which parts is what keeps the
overlay small enough to read.

| | Development | Production | Why it differs |
|---|---|---|---|
| Namespace | `twentyfour` | `twentyfour` | Nothing. One market per machine, so the namespace carries no meaning |
| Registry | `localhost:5000` | a real registry | One is a container on this laptop |
| Image tag | `:dev`, moving | a git SHA, fixed | See **Image tags** below. This is the one place the obvious answer is wrong |
| Hosts | `*.twentyfour.localhost`, HTTP | real domains, TLS | Certificates exist for one and not the other |
| Cookies | not `Secure`, host-only | `Secure`, parent domain | A session cookie over HTTP is a session anyone on the path can take |
| RBAC | `-permissive=true` | `-permissive=false` | Development walks the dashboard before the roles are seeded |
| Network policy | none | default deny | The architecture's invariant. See below |
| Secrets | generated by a script | OpenBao | `devpassword` is in git history already and should stay a development-only string |
| Postgres | one StatefulSet | CloudNativePG with PITR | A volume that survives a restart is not a backup |
| Replicas | 1 | per service | Availability during a rollout |
| Kafka topics | auto-created, 1 partition | created deliberately | Partition count cannot be lowered afterwards |
| Payment desk | routed at `/pay` | absent | A page where a person approves payments, unauthenticated |
| Message desk | port-forward only | absent | Shows every tenant's messages |
| Seed scripts | present | absent | They create accounts |
| Cluster monitor | can stop and rebuild | `-read-only` | A stop button beside production |

Everything not in that table is the same file.

## The mechanism: Kustomize

`deploy/` becomes a base, and each environment is an overlay that patches it.

```
platform/deploy/
  base/            everything that is true everywhere, as it is written today
    infra/  apps/  web/
  environments/
    dev/           kustomization.yaml + patches + env
    prod/          kustomization.yaml + patches + env + the resources only prod has
```

Applied with `kubectl apply -k deploy/environments/dev`, which needs no binary
that is not already required. That matters: §17 asks for a reason before adding
a dependency, and this adds none.

**Helm was considered and rejected.** These manifests carry long comments
explaining why each field is what it is, and those comments are the closest
thing the deployment has to documentation. Turning them into templates would
make the most-read files in `deploy/` unreadable, and it would buy templating
that overlays already do without a language.

**An overlay is not only a patch.** Production has resources development does
not: NetworkPolicy, HorizontalPodAutoscaler, PodDisruptionBudget, a CloudNativePG
cluster in place of a StatefulSet, a topic-creation Job. Those are files in the
prod overlay, not conditionals in a shared file. Nothing in the base ever says
`if prod`.

## The environment file

Each environment carries one file of values, and the scripts read it.

```sh
# platform/deploy/environments/prod/env
TF_ENV=prod
NAMESPACE=twentyfour
REGISTRY=registry.twentyfour.hu/twentyfour
APP_HOST=app.twentyfour.hu
ADMIN_HOST=admin.twentyfour.hu
MEDIA_HOST=media.twentyfour.hu
CURRENCY=HUF
# The context this environment lives in. Every command refuses to run against
# any other, which is the guard that actually works.
KUBE_CONTEXT=twentyfour-hu
```

The scripts already read `deploy/inventory.tsv` and glob for Containerfiles, so
sourcing one more file fits what they do. `NS=twentyfour` and
`REG=localhost:5000/twentyfour` stop being literals at the top of
`scripts/system.sh` and become values from the selected environment.

### The guard that matters

A namespace check does not catch the real mistake, which is the right command in
the wrong terminal against the wrong cluster. So every command asserts the
context:

```sh
[ "$(kubectl config current-context)" = "$KUBE_CONTEXT" ] || {
  echo "This is $ENV, whose context is $KUBE_CONTEXT."
  echo "You are pointed at $(kubectl config current-context)."
  exit 1
}
```

That is cheap, and it is the difference between `make down` being a typo and
being an outage.

## The commands

`ENV` selects, and **it defaults to `dev`**. Production is never what happens
when you forget to say.

```bash
make up                  # dev
make up ENV=prod         # prod, once phase 4 lands
make status ENV=prod     # identical behaviour, read-only
make check ENV=prod
```

| Command | dev | prod |
|---|---|---|
| `status`, `api-status`, `check`, `logs` | same | same |
| `up`, `down`, `restart` | applies directly | phase 1: same, with a typed confirmation. Phase 5: refuses, and tells you to promote |
| `rebuild`, `<service>-up REBUILD=1` | builds from source | refuses. Production runs what was built and tested, not what is in this working copy |
| `seed-account`, `pay-desk` | present | refuse outright, by name |

The read-only half of the promise is exact: `make status ENV=prod` and
`make status` are the same code path against a different cluster. The half that
writes is not, and pretending otherwise is how a laptop's working copy reaches
a merchant.

## Image tags: the one place `:prod` is wrong

`:dev` is right for development. A matching `:prod` is not, and it is worth
being blunt about why.

A moving tag plus `imagePullPolicy: Always` means **a pod that restarts at three
in the morning runs a different binary from the pods beside it**, and nothing
records that it happened. It also means "roll back" has no referent: there is no
name for the thing that was working an hour ago.

So:

- **dev** stays `:dev`, mutable, because iteration speed is the whole point and
  nothing is at risk.
- **prod** is tagged with the git SHA at build time, and the overlay pins it.
  Rolling back is editing one line to a SHA that exists.

```sh
# build once, tag by what it is
podman build -t $REGISTRY/pos:$(git rev-parse --short HEAD) ...
```

Promotion is then a mechanical act: `make promote ENV=prod SHA=abc1234` writes
the SHA into the prod overlay's image list. Under Argo CD (phase 5) that is a
commit, and the commit is the deployment record.

## What must never reach production

Some of what is built is deliberately unsafe and says so in its own source. The
payment desk is unauthenticated by design, because whoever is at the terminal is
the customer; the message desk shows every tenant's messages, because a provider
sees everything it was asked to carry. Both are correct for what they are and
both must be absent from a real deployment.

An overlay that forgot one of these would look fine. So the check is mechanical:
render the prod overlay and fail the build if any of these appear.

```sh
# scripts/prod-preflight.sh, run before any prod apply
kubectl kustomize deploy/environments/prod > /tmp/prod.yaml
forbidden='localhost:5000|devpassword|permissive=true|secure-cookie=false|PathPrefix\(`/pay`\)|desk-addr'
grep -nE "$forbidden" /tmp/prod.yaml && { echo "development-only surface in a production manifest"; exit 1; }
```

The frontend needs the same treatment: the auth application's demo account
picker is a lazily imported chunk, which keeps it out of the main bundle but not
out of the build. Production builds must drop it, and the check should assert
the built bundle does not contain it rather than trusting that it does not.

## Phases

Each phase leaves the system working, and only the last one touches a real
machine.

### Phase 0. Parameterise, changing nothing

Move `deploy/` under `base/`, add the `dev` overlay, extract the 70 hardcoded
values into `environments/dev/env`. Scripts source it.

*Done when:* `make system-up` and `make system-status` behave exactly as they do
today, and `git diff` shows no manifest changed in meaning. This phase is
finished when nothing has changed, which is the only way to know the
parameterisation is faithful.

### Phase 1. The prod overlay, rendered and never applied

Write `environments/prod`, the resources production adds, and
`scripts/prod-preflight.sh`. Nothing is deployed.

*Done when:* `make render ENV=prod` produces a complete manifest set, preflight
passes, and a person can read the rendered output and see what production would
be. **This is where the work stops until a machine exists.**

### Phase 2. Turn the safeties on in development first

This is the phase most likely to be skipped and the most valuable.

- Set `-permissive=false` in **dev** and fix what breaks. Every permission check
  in the platform has been passing unconditionally since it was written, so this
  is the first time any of them is exercised.
- Add NetworkPolicy in **dev**: default deny, then allow exactly the edges the
  cluster monitor now draws. The graph is the specification.
- Give the migration race an answer. Every service migrates on start and goose
  is configured without a session lock, so two replicas would race the first
  time production runs two of anything. The smallest fix is
  `goose.WithSessionLocker()` in `packages/pg`, which keeps the self-migrating
  property the whole repo is built on; the alternative is a migration Job per
  service, which is more moving parts for the same result.

*Done when:* dev runs with permissive off and default-deny networking, and the
system still passes `make check`. Discovering what permissive was hiding on the
day production first exists is the outcome this phase prevents.

### Phase 3. The data tier

- CloudNativePG in place of the Postgres StatefulSet, with PITR and a tested
  restore. An untested restore is not a backup.
- A topic-creation Job with chosen partition counts and retention, and
  `AllowAutoTopicCreation` off in production. **Partitions cannot be lowered
  later**, and they are the ceiling on how far the ledger, the audit trail and
  the kitchen can scale: one active consumer per partition, whatever the replica
  count.
- ClickHouse and MinIO sizing, and a backup for each.
- OpenBao, and secrets that are references rather than literals.

### Phase 4. First production apply, by hand, watched

One host, one market. Applied manually so that the first time is observed rather
than automated. Observability comes up before the services do, because a
deployment you cannot see is a deployment you cannot judge: Prometheus, Grafana,
Loki, Tempo, OpenTelemetry and GlitchTip are all in §17 and none is deployed
anywhere yet.

### Phase 5. Argo CD, and prod stops being a command

Argo watches the prod overlay. `make up ENV=prod` starts refusing and points at
`make promote`. Git becomes the record of what is running, which is the
architecture's stated end state and the thing that makes a second market a
repeat rather than a rewrite.

## Decisions taken

| Question | Decision |
|---|---|
| Templating | **Kustomize overlays.** No new dependency, and the commented base stays readable |
| Environment selector | **`ENV=`, defaulting to `dev`.** Production is never the default |
| Wrong-cluster guard | **Assert the kube context**, not the namespace. It catches the mistake people actually make |
| Production image tag | **Git SHA, immutable.** Never a moving `:prod` |
| Production rebuilds | **Refused.** Production runs what was built and tested |
| Dev-only surfaces | **A grep over the rendered manifest that fails the build**, not a convention |
| Namespace | **The same in both.** One market per machine, so it distinguishes nothing |
| Safety features | **Enabled in development first**, so their consequences are found before a merchant exists |
| Staging | **There is none.** Two environments, not three. Development is where a change is proved, and the first production deploy is watched rather than rehearsed. A third environment is a third set of everything on a third machine, and the thing it would catch is caught by phase 2 instead |

## Open questions

1. **How many partitions.** It has to be chosen before the first production
   deploy and cannot be reduced afterwards. It is also the hard ceiling on
   consumer scaling, so it should be picked from expected order volume rather
   than from a default.
2. **Where the registry lives.** A registry per market means an image built once
   and pushed twice, and a shared one means every market can pull every other
   market's builds. Both are defensible; neither is chosen.
3. **What the first production deploy is missing.** The storefront plane is not
   built, so the first deploy serves two planes rather than three, and the six
   unbuilt services simply do not appear because `inventory.tsv` already drives
   that. Whether that is a launch or a pilot is a product decision, not an
   infrastructure one.
4. **Migration strategy under rollout.** Phase 2 settles the race between
   replicas. It does not settle what happens when a migration is not backward
   compatible with the pods still running the previous image, which needs the
   expand-and-contract discipline written down before the first schema change
   that would break it.
